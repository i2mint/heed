heed#

heed — embeddable, no-install, framework-agnostic end-user feedback.

heed lets any visitor of a deployed web app report a bug or request a feature, with useful context gathered automatically, routed to a pluggable backend (GitHub Issues first). It works standalone and integrates with enlace as an optional add-on; the only part of enlace it uses is the stdlib-only enlace.ratelimit (trusted-proxy client address and limiters), shared so the mechanism is implemented once.

Phase 1 ships the backend core and the embeddable widget (widget/, served by make_widget_router()). The competitive landscape and design rationale live in misc/docs/.

Public API (Phase 1):
Models Report, ReportSubmission, Identity, Environment, Category, Status,

Attachment, LogEntry, NetEntry

Sinks Sink, BaseSink, SinkResult, StoreSink, GitHubIssuesSink,

github_sink_from_token

Backend process_submission, make_router, make_app, HeedConfig Hardening RateLimiter, InMemoryRateLimiter, RedisRateLimiter, make_rate_limiter,

BotVerifier, SiteverifyBotVerifier, make_bot_verifier, make_image_sanitizer, strip_image, reencode_image, attachment_headers (see misc/docs/embedding-security.md)

Privacy redact_text, redact_url (masking of opt-in console/network capture) Routing sinks_by_origin, Verdict, accept_all, hold_all,

make_heuristic_moderator, chain_moderators, release_held, recover_claimed, discard_held

Storage make_report_store, make_holding_store, make_attachment_store Serving make_attachment_router, make_attachment_app, AttachmentSigner,

screenshot_url_resolver (a separate origin for screenshots, #19)

Widget make_widget_router (serves the built embeddable widget),

widget_contract (what the widget sends; SSOT for widget/)

Threads Comment, CommentSubmission, add_comment, list_comments,

delete_comment, email_moderator, token_moderator, make_thread_router (a public, persistent comment thread per key)

Review ReviewPage, publish_review, review_url, make_review_app (media + a

thread under it, behind a capability link; CLI heed review)

Triage triage, Triage, Severity (a proposal per report: injected LLM,

fenced and whitelisted, or keyword rules without one); find_duplicates, mark_duplicate (retrieval + optional confirmation; marking is explicit, never a silent merge); FeedbackQueue (list / get / triage / dedup / create / close; heed.mcp serves it over MCP)

Example

>>> from heed import StoreSink, ReportSubmission, process_submission
>>> store = {}
>>> report, result = process_submission(
...     ReportSubmission(title="Login button does nothing"), StoreSink(store)
... )
>>> result.ok and report.id in store
True

class heed.AttachmentSigner(key, *, previous_keys=(), ttl_seconds=None, clock=<built-in function time>)[source]#

Bases: object

Mint and check signed attachment URLs (HMAC-SHA256 over the ref and expiry).

ttl_seconds=None (the default) signs URLs that never expire: a GitHub issue keeps showing its screenshot, and access is revoked by deleting the attachment or rotating the key. A ttl makes URLs expire, which suits links handed to people rather than embedded in issues. previous_keys still verify (never sign), for rotation.

>>> s = AttachmentSigner("k" * 32, ttl_seconds=60, clock=lambda: 1000)
>>> q = s.sign("ab.png")
>>> q["exp"], s.verify("ab.png", **q), s.verify("other.png", **q)
('1060', True, False)
>>> later = AttachmentSigner("k" * 32, ttl_seconds=60, clock=lambda: 2000)
>>> later.verify("ab.png", **q)
False

class heed.RedisRateLimiter(client, *, max_per_window=30, window_seconds=60.0, namespace='heed:rl', fallback=None, max_keys=100000, clock=<built-in function time>)[source]#

Bases: _WindowKnobs, RedisLimiter

Fixed-window limiter in Redis — one count shared by every worker and host.

client is any redis-py compatible client (injected; tests use a fake). When Redis errors, the request is decided by fallback (a per-process in-memory limiter by default), so an outage degrades protection instead of either dropping all feedback or removing the limit. from_url() builds the client from a redis:// URL (needs the [redis] extra).

After a Redis error the fallback alone decides for retry_seconds (5 s by default) before Redis is tried again, so a hung Redis costs one socket timeout per interval, not one per request; one warning per outage is logged, on the enlace.ratelimit logger. An allow-only fallback is wrapped to answer acquire too, so .fallback is then that wrapper (its .limiter is yours). Counters are named {namespace}:{window}:{key}:{window number}.

heed.make_attachment_router(attachment_store, *, config=None, signer=None, allow_unsigned=False, allowed_hosts=None, cross_origin=False, cache_control=None, max_bytes=None, path='/attachments', ref_pattern=re.compile('[0-9a-f]{32}\\.(?:png|jpg|webp)'))[source]#

A router serving GET {path}/{ref} from attachment_store, read-only.

Every response that returns bytes carries attachment_headers; the bytes are re-sniffed, and anything that is not the image its extension names is sent as an opaque download. A missing, malformed, unsigned or expired ref is the same bare 404, so the route is no oracle for which reports exist; a wrong Host is a 421 (a deployment error worth seeing). Behind a reverse proxy, the Host checked is the one the proxy forwards: keep it the browser’s (Caddy and nginx can).

Parameters:

  • attachment_store (Mapping[str, bytes]) – Where process_submission put the screenshots.

  • config (HeedConfig | None) – Defaults for signer (attachment_signing_key, attachment_url_ttl_seconds) and allowed_hosts (attachment_hosts).

  • signer (AttachmentSigner | None) – Required unless allow_unsigned: report ids are not secret.

  • allow_unsigned (bool) – Serve any ref without a signature (a ref is then the capability). Only for stores whose every screenshot may be public.

  • allowed_hosts (Iterable[str] | None) – Hostnames this route answers on: the dedicated attachment origin. Required (here or as config.attachment_hosts): ANY_HOST says any host is fine, which is only right when the route has no origin of its own.

  • cross_origin (bool) – Cross-Origin-Resource-Policy: cross-origin, which an image embedded in a GitHub issue needs (GitHub’s camo proxy fetches it).

heed.recover_claimed(*, holding_store, claimed_store=None, stale_after=None, clock=<built-in function time>)[source]#

Return every claimed report to holding, and the ids returned.

A claim outlives its release_held() only if the process died mid-release (the sink may or may not have accepted the report, so a recovered report may be sent twice – never zero times). Pass the same claimed_store as to release_held().

An in-flight release’s claim looks the same as a stranded one. With one process, call this when no release is running (e.g. at startup) and leave stale_after unset: every claim is recovered. With several workers, one worker’s startup can overlap another’s release, so pass stale_after (seconds; longer than any sink call can take plus the clock skew between workers, e.g. 600): only claims older than that are recovered (and claims stamped further ahead than that, by a clock running fast). Claims made before claim keys carried a time count as stale. A release whose claim is recovered anyway puts the report back in holding and fails. Beside a dedicated claims store, claimed-- claims an older heed left in holding are recovered too (which lists holding once).

Only a valid report (whose own id matches its claim key) is ever written to holding, and a valid holding copy is never replaced: a claim whose report is intact in holding is just dropped (even a torn one), and one whose holding copy is torn or missing restores it. Otherwise a claim that is not a valid report is left in place, and not returned.

list[str]

heed.release_held(report_id, *, holding_store, sink=None, resolve_sink=None, claimed_store=None, clock=<built-in function time>)[source]#

Release a held report: route it on and remove it from holding.

holding_store is the store behind the holding sink (a StoreSink’s .store). The destination is sink, or — for a multi-site backend — the sink resolve_sink gives for the report’s own origin (pass exactly one).

The report is claimed before submitting, so a second release while the first is in flight finds nothing to send. Claiming moves it: it is written under a claim key of its own (<id>--<time>-<token>) in the claims store and only then deleted from holding. The claims store is claimed_store if given, else the one a make_holding_store store carries, else (legacy) holding_store itself under a claimed-- prefix – which makes every release list the whole holding store. If the sink fails the report is put back in holding; a release only ever deletes its own claim, and only once the sink has accepted the report or it is back in holding. So a crash at any point leaves the report in holding, in the claims, or in both – never lost – and recover_claimed() returns stranded claims to holding. A report with a claim is not released again until then.

Not safe against two releases of the same report at the same moment: claiming is a copy and a delete on a plain mapping, not an atomic move, so one interleaving leaves a claim on a report the other release already sent, and the next recover_claimed() sends it again. Serialise releases of one report.

heed.token_moderator(token, *, also=None)[source]#

A moderator check that needs a secret the owner types in, not a login.

On an origin shared with other apps, a session cookie is ambient authority: any script running there while the owner is logged in can call the API as the owner. A secret in a request header is not ambient (the review page keeps it in memory, never in storage), so such a script can neither delete comments nor post badged as the owner. also (e.g. email_moderator()) is required too, when given.

Use a random token (secrets.token_urlsafe(24)). This raises the bar, it is not a wall: a hostile script on the same origin can still open the review page in a frame and hook it before the owner types the token, or phish with its own prompt. A dedicated origin for the review app is the real fix.
