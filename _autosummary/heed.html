heed#

heed — embeddable, no-install, framework-agnostic end-user feedback.

heed lets any visitor of a deployed web app report a bug or request a feature, with useful context gathered automatically, routed to a pluggable backend (GitHub Issues first). It works standalone and integrates with enlace as an optional add-on, without depending on it.

Phase 1 ships the backend core (the widget is tracked in issue #6). The competitive landscape and design rationale live in misc/docs/.

Public API (Phase 1):
Models Report, ReportSubmission, Identity, Environment, Category, Status,

Attachment, LogEntry, NetEntry

Sinks Sink, BaseSink, SinkResult, StoreSink, GitHubIssuesSink,

github_sink_from_token

Backend process_submission, make_router, make_app, HeedConfig Hardening RateLimiter, InMemoryRateLimiter, RedisRateLimiter, make_rate_limiter,

BotVerifier, SiteverifyBotVerifier, make_bot_verifier (see misc/docs/embedding-security.md)

Storage make_report_store, make_attachment_store

Example

>>> from heed import StoreSink, ReportSubmission, process_submission
>>> store = {}
>>> report, result = process_submission(
...     ReportSubmission(title="Login button does nothing"), StoreSink(store)
... )
>>> result.ok and report.id in store
True

class heed.InMemoryRateLimiter(*, max_per_window=30, window_seconds=60.0, max_keys=100000, clock=<built-in function monotonic>)[source]#

Bases: object

Sliding-window, in-memory limiter. Per process — NOT shared across workers.

Fine for a single-worker deployment; with several workers each one counts alone, so the effective limit is multiplied. Use RedisRateLimiter there. The number of tracked keys is bounded (max_keys, least-recently-seen evicted) so a flood of distinct keys cannot exhaust memory.

class heed.RedisRateLimiter(client, *, max_per_window=30, window_seconds=60.0, namespace='heed:rl', fallback=None, clock=<built-in function time>)[source]#

Bases: object

Fixed-window limiter in Redis — one count shared by every worker and host.

client is any redis-py compatible client (injected; tests use a fake). When Redis errors, the request is decided by fallback (a per-process in-memory limiter by default), so an outage degrades protection instead of either dropping all feedback or removing the limit.

heed.make_router(sink, *, config=None, attachment_store=None, rate_limiter=None, origin_rate_limiter=None, bot_verifier=None, user_dependency=None)[source]#

Build a FastAPI APIRouter exposing POST /report (and its CORS preflight).

Run standalone via make_app(), or include_router it into an enlace app. Provide user_dependency (a FastAPI dependency returning a user id or None) to bind identity when an auth layer like enlace_auth is present.

Hardening defaults come from config; any piece can be injected instead: rate_limiter (per client IP), origin_rate_limiter (per Origin) and bot_verifier (by default built from config.bot_secret, i.e. off until a secret is configured).

Return type:

APIRouter
