heed.review#

Review pages: media (a video, audio, images) with a comment thread under it.

Publish one or more media files under a title and get a link; whoever has the link watches the media and reads and adds comments (a name per comment, optionally pinned to a moment in the video), on every visit, without an account. The owner deletes comments, over HTTP when is_moderator says so or from the CLI. On an origin shared with other apps, use token_moderator (a typed-in secret) rather than a login alone: a login is ambient, so any script on that origin acts as the owner (#74).

The link is a capability: the page id is 128 random bits and travels in the URL fragment (https://host/review/#<id>), so the link itself is never sent in a request or a Referer (the API calls the page makes do carry the id in their paths, so the host’s access logs see it). Without the id a page, its media and its thread are all 404s. On top of that the thread endpoint is rate-limited per IP and per thread, capped per thread, size-capped, and has a honeypot (see heed.threads).

Layout of the data root (one folder; ADR-0024’s S3 layout mirrors it key for key):

pages/<id>.json            the page: title, note, media list, created_at
media/<id>/<name>          the media files, served with byte ranges (seekable)
comments/<id>/<cid>.json   the thread (heed.threads)
access/<id>.json           optional password, expiry, revoke (heed.review_access);
                           no file means open: back this folder up too

Python:

>>> import tempfile
>>> root = tempfile.mkdtemp()
>>> clip = os.path.join(root, "cut1.mp4"); _ = open(clip, "wb").write(b"\0" * 10)
>>> page = publish_review([clip], title="Plot car, cut 1", rootdir=root)
>>> [m.name for m in page.media], len(page.id)
(['cut1.mp4'], 22)
>>> url = review_url(page.id, "https://apps.example/review/")
>>> url == "https://apps.example/review/#" + page.id
True

CLI: heed review publish cut1.mp4 --title "Plot car" prints the link; heed review comments <id> reads the thread back (--json for agents).

The review API (and, with serve_shell, the page at /).

Routes: GET /pages/{id}, GET /pages/{id}/media/{name} (byte ranges; ?download=1 serves it as an attachment, so a phone saves the file), GET|POST /threads/{id}, DELETE /threads/{id}/{comment} (moderators), GET /ui/review.{js,css}. There is deliberately no HTTP listing of pages: it would hand every capability to any script running as the owner (the CLI’s ls lists them).

A page given a password, an expiry or a revoke (publish_review(), heed review revoke) is gated by gate (a ReviewGate, built over rootdir with trusted_proxies by default): 401 until POST /pages/{id}/unlock {"password": ...} sets a cookie, 410 once expired, 404 once revoked. Pages with no such record are open, as ever.

heed.review.publish_review(media, *, title=None, note=None, rootdir=None, to=None, password=None, expires=None)[source]#

Publish media as a new review page (or add it to page to).

password and expires ("7d", "2026-11-01", "never") gate the page (heed.review_access, needs heed[gate]); on an existing page they change only what is given. Neither: the page is open to whoever has the link.

The files are copied into the data root. Adding to an existing page keeps its link and its thread, so a new cut can go where the old one’s comments are; a file with the name of one already on the page replaces it.
