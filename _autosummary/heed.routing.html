heed.routing#

Where a report goes: server-side site resolution and moderation (holding state).

Two seams, both decided on the server, never by the browser:

  • Site resolution: a SinkResolver maps the validated request origin to the sink for that site (e.g. which GitHub repo). The widget never names a target, so a visitor cannot redirect reports into someone else’s tracker. sinks_by_origin() builds one from a plain mapping.

  • Moderation: a Moderator looks at a server-enriched report and returns a Verdict. hold parks the report in a holding sink (status held)

    until a human releases it with release_held(); reject drops it.

    accept_all() is the default, hold_all() gives full pre-moderation, and make_heuristic_moderator() holds link floods and blocked terms.

heed.routing.discard_held(report_id, *, holding_store, attachment_store=None)[source]#

Delete a held report for good, with its attachments (e.g. a screenshot).

The report leaves holding first, so a release that took it meanwhile wins and this raises KeyError before touching its attachments; a crash between the two steps leaves an orphaned screenshot, never a report pointing at a deleted one. Raises KeyError when report_id is not held. A report whose text no longer parses is still deleted, but its attachments cannot be named and are left. Run it serialised with release_held() for the same report.

Cheap, dependency-free spam signals. Holding (not rejecting) is the default so a false positive costs a human click, not a lost report.

heed.routing.recover_claimed(*, holding_store, claimed_store=None, stale_after=None, clock=<built-in function time>)[source]#

Return every claimed report to holding, and the ids returned.

A claim outlives its release_held() only if the process died mid-release (the sink may or may not have accepted the report, so a recovered report may be sent twice – never zero times). Pass the same claimed_store as to release_held().

An in-flight release’s claim looks the same as a stranded one. With one process, call this when no release is running (e.g. at startup) and leave stale_after unset: every claim is recovered. With several workers, one worker’s startup can overlap another’s release, so pass stale_after (seconds; longer than any sink call can take plus the clock skew between workers, e.g. 600): only claims older than that are recovered (and claims stamped further ahead than that, by a clock running fast). Claims made before claim keys carried a time count as stale. A release whose claim is recovered anyway puts the report back in holding and fails. Beside a dedicated claims store, claimed-- claims an older heed left in holding are recovered too (which lists holding once).

Only a valid report (whose own id matches its claim key) is ever written to holding, and a valid holding copy is never replaced: a claim whose report is intact in holding is just dropped (even a torn one), and one whose holding copy is torn or missing restores it. Otherwise a claim that is not a valid report is left in place, and not returned.

Return type:

list[str]

heed.routing.release_held(report_id, *, holding_store, sink=None, resolve_sink=None, claimed_store=None, clock=<built-in function time>)[source]#

Release a held report: route it on and remove it from holding.

holding_store is the store behind the holding sink (a StoreSink’s .store). The destination is sink, or — for a multi-site backend — the sink resolve_sink gives for the report’s own origin (pass exactly one).

The report is claimed before submitting, so a second release while the first is in flight finds nothing to send. Claiming moves it: it is written under a claim key of its own (<id>--<time>-<token>) in the claims store and only then deleted from holding. The claims store is claimed_store if given, else the one a make_holding_store store carries, else (legacy) holding_store itself under a claimed-- prefix – which makes every release list the whole holding store. If the sink fails the report is put back in holding; a release only ever deletes its own claim, and only once the sink has accepted the report or it is back in holding. So a crash at any point leaves the report in holding, in the claims, or in both – never lost – and recover_claimed() returns stranded claims to holding. A report with a claim is not released again until then.

Not safe against two releases of the same report at the same moment: claiming is a copy and a delete on a plain mapping, not an atomic move, so one interleaving leaves a claim on a report the other release already sent, and the next recover_claimed() sends it again. Serialise releases of one report.

Return type:

SinkResult

heed.routing.sinks_by_origin(sinks, *, default=None)[source]#

A resolver from an {origin: sink} mapping (origins compared normalized).

Unknown origins resolve to default; with no default they resolve to None, and the router refuses them.

>>> from heed.sinks import StoreSink
>>> a = StoreSink({})
>>> resolve = sinks_by_origin({"https://a.example": a})
>>> resolve("HTTPS://A.example/") is a, resolve("https://b.example")
(True, None)
