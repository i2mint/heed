heed.security#

Public-endpoint hardening (the ingest endpoint is unauthenticated and hostile).

Everything here is a small function or a strategy behind a protocol, so the router composes them and deployments swap implementations without touching it:

  • Origins / CORS: origin_allowed(), cors_headers(), preflight_headers().

  • Client identity for rate limiting: client_ip() (honours X-Forwarded-For only from trusted proxies).

  • Rate limiting: the RateLimiter protocol, an in-memory default (InMemoryRateLimiter, per process) and RedisRateLimiter (shared across workers), looked up by name via make_rate_limiter().

  • Bot gate: the BotVerifier protocol and SiteverifyBotVerifier for Cloudflare Turnstile / hCaptcha, built by make_bot_verifier() only when a secret is configured (off otherwise).

  • Attachments: sniff_image_type() checks screenshot magic bytes (and images.py rewrites them); attachment_headers() is how to serve them.

class heed.security.InMemoryRateLimiter(*, max_per_window=30, window_seconds=60.0, max_keys=100000, clock=<built-in function monotonic>)[source]#

Bases: object

Sliding-window, in-memory limiter. Per process — NOT shared across workers.

Fine for a single-worker deployment; with several workers each one counts alone, so the effective limit is multiplied. Use RedisRateLimiter there. The number of tracked keys is bounded (max_keys, least-recently-seen evicted) so a flood of distinct keys cannot exhaust memory.

Bases: object

Fixed-window limiter in Redis — one count shared by every worker and host.

client is any redis-py compatible client (injected; tests use a fake). When Redis errors, the request is decided by fallback (a per-process in-memory limiter by default), so an outage degrades protection instead of either dropping all feedback or removing the limit.

heed.security.attachment_headers(media_type, *, filename=None, cross_origin=False)[source]#

Headers for serving a stored screenshot (issue #15). Use them on every response that returns attachment bytes, ideally from an origin separate from the app’s.

Only the image types heed accepts are served as themselves; anything else is sent as an opaque download. Embedding is limited to the same site (Cross-Origin-Resource-Policy: same-site) unless cross_origin=True, which a screenshot embedded elsewhere (e.g. in a GitHub issue) needs.

Return type:

dict

>>> h = attachment_headers("image/png", filename="r1.png")
>>> h["Content-Type"], h["X-Content-Type-Options"], h["Content-Disposition"]
('image/png', 'nosniff', 'inline; filename="r1.png"')
>>> attachment_headers("text/html")["Content-Type"]
'application/octet-stream'
heed.security.client_ip(peer, forwarded_for, *, trusted_proxies=())[source]#

The client address to rate-limit on.

X-Forwarded-For is attacker-controlled unless the direct peer is a trusted proxy, so it is only consulted then — and read right-to-left, skipping trusted hops, so a client cannot prepend a fake address.

Return type:

str

>>> client_ip("10.0.0.1", "6.6.6.6, 1.2.3.4", trusted_proxies=["10.0.0.0/8"])
'1.2.3.4'
>>> client_ip("5.5.5.5", "1.2.3.4")  # untrusted peer: header ignored
'5.5.5.5'

heed.security.rate_limit_key(ip, *, ipv6_prefix=64)[source]#

The bucket key for ip: IPv4 as-is, IPv6 grouped by its /ipv6_prefix.

One IPv6 host typically owns a whole /64, so per-address buckets are trivially dodged by rotating addresses.

Return type:

str

>>> rate_limit_key("2001:db8::1") == rate_limit_key("2001:db8::ffff")
True
>>> rate_limit_key("1.2.3.4")
'1.2.3.4'
